Flow control and error control

  • Together they are called data link control (DLC)
  • Flow control: a fast sender must not overwhelm a slow receiver
  • Error control: damaged frames are discarded; lost ones must be resent
  • Data link error control is ARQ: automatic repeat request
  • Both need feedback from the receiver: ACKs (and sometimes NAKs)

Flow control

How much may the sender send before it must wait for an acknowledgement? Protects the receiver's buffer.

Error control

Detect lost or damaged frames and resend them: automatic repeat request (ARQ).

On a perfect channel: Simplest and Stop-and-Wait

  • Simplest: send whenever there is data; no ACK, no flow control
  • Assumes the receiver can process every frame immediately
  • Stop-and-Wait: send one frame, then stop until its ACK arrives
  • The ACK is the receiver's permission to send the next one
  • Flow control only: on a perfect channel, nothing is lost

Stop-and-Wait ARQ

  • Real (noisy) channel: frames and ACKs can be lost or damaged
  • Sender keeps a copy of the frame and starts a timer
  • Time-out before the ACK? Resend the copy
  • Frames are numbered 0, 1, 0, 1 … so duplicates can be recognised
  • ACK n means “I expect frame n next”

Stop-and-Wait ARQ in action

  • Frame 0 is sent and acknowledged (ACK 1)
  • Frame 1 is lost: no ACK; the timer expires; frame 1 is resent

  • Sender cannot tell which was lost: it resends frame 0
  • Receiver expects 1, sees 0: a duplicate. Discard it, send ACK 1 again

Why Stop-and-Wait wastes a fast link

  • Rate 1 Mbps; a bit takes 20 ms to go and come back
  • Bandwidth-delay product = bits the link can hold during one round trip
  • Stop-and-Wait sends 1,000 bits per round trip: 5% utilisation
  • Letting 15 frames be in flight: 75%
  • Fast or long links (satellite, fibre) need many frames in flight: pipelining

One round trip could carry 20 frames of 1,000 bits; Stop-and-Wait sends one

Link utilisation: the general formula

  • Tt = L / R (transmission time); Tp = propagation time
  • One cycle = Tt + 2Tp; a window of W frames fills W·Tt of it
  • Stop-and-Wait (W = 1): U = 1 / (1 + 2a)
  • The longer or faster the link, the larger a, and the bigger W must be
  • W needs enough sequence numbers: the window-size rules come later

a = Tp / Tt

U = W / (1 + 2a), at most 1

Full use: W ≥ 1 + 2a

Sliding windows and sequence numbers

  • Pipelining needs many numbered frames in flight
  • With an m-bit field, numbers run 0 … 2m − 1, then repeat
  • The send window covers frames sent but not yet ACKed, plus those it may still send
  • Sf: first outstanding · Sn: next to send · Ssize: window size
  • An ACK slides the window forward; the sender may then send more

Go-Back-N ARQ

  • Up to Ssize frames may be outstanding; Ssize ≤ 2m − 1
  • Receiver window = 1: frames must arrive in order; others are discarded
  • ACKs are cumulative: ACK n confirms all frames before n
  • On time-out the sender goes back and resends every outstanding frame
  • Simple receiver (no buffering); wasteful when errors are frequent

Go-Back-N: why Ssize < 2m

  • Worst case: a full window arrives, but every ACK is lost
  • Receiver has moved on; sender times out and resends its oldest frame
  • If the window used all 2m numbers, the old frame's number is exactly the one the receiver expects next
  • So the send window must be at most 2m − 1
  • m = 3 → window ≤ 7; m = 4 → ≤ 15

Selective Repeat ARQ

  • Receiver keeps a window too, and stores out-of-order frames

  • Sender resends only that frame (NAK or its own timer)

  • Both windows ≤ 2m−1; more buffers and logic at the receiver

Selective Repeat in action

  • Frame 1 is lost; frames 2 and 3 arrive and are stored

  • Compare Go-Back-N: 3 frames resent instead of 1

Selective Repeat: why the window is ≤ 2m−1

  • Same worst case: the frames arrive, every ACK is lost
  • The receiver's window has slid forward by a whole window
  • If the two windows overlap, an old number falls inside the new window
  • No overlap needs send + receive window ≤ 2m, so each ≤ 2m−1
  • m = 3 → 4 (Go-Back-N could use 7)

Piggybacking

  • Real links carry data in both directions
  • Each data frame carries an ACK field for the other direction
  • So B's next data frame acknowledges A's frames: no separate ACK frame
  • No data to send? Wait briefly, then send an ACK frame on its own
  • In HDLC the N(R) field of an I-frame is the piggybacked ACK

PPP: the Point-to-Point Protocol

  • The common protocol for point-to-point links (dial-up, DSL via PPPoE, router links)
  • Byte-oriented, with an HDLC-like frame
  • Address FF and control 03 are constants: no stations, no numbering
  • Protocol field says what the payload is (IP, LCP, PAP …)
  • Errors are only detected (FCS); recovery is left to upper layers

PPP byte stuffing

  • PPP's flag is a whole byte: 7E = 01111110
  • A data byte equal to 7E or 7D (escape) must be escaped
  • Escape byte 7D = 01111101
  • Real PPP also changes the escaped byte: XOR with 20
  • Receiver: drop 7D, XOR the next byte with 20

Key takeaways

  • Flow control protects the receiver; error control (ARQ) resends what is lost
  • Stop-and-Wait ARQ: copy, timer, numbers 0/1; U = 1/(1 + 2a)
  • Go-Back-N: window ≤ 2m − 1, receiver window 1, resend from the loss
  • Selective Repeat: windows ≤ 2m−1, NAK, resend only the lost frame
  • Piggybacking puts ACKs in data frames; HDLC (I/S/U frames) and PPP use these ideas
